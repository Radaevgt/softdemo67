# Портал работы с заброшенными объектами

Веб-портал для сотрудников ОМСУ: определение способа оформления права муниципальной
собственности на неиспользуемый ОКС или понуждения собственника к сносу.

Реализован **этап 4** технического задания. Сотрудник вводит сведения об объекте, собранные на
этапах 1–3, проходит адаптивный опрос и получает сценарий, способ оформления и порядок действий
в виде рабочей дорожной карты.

Аналитическая записка с разбором ТЗ — [`docs/analysis.md`](docs/analysis.md).

Есть упрощённая версия того же — **бот в мессенджере MAX**: те же 61 сценарий и тот же опрос, но
без учётных записей и без базы. Описание — [`docs/max-bot.md`](docs/max-bot.md).

## Возможности

- **Реестр объектов** с фильтрами по виду, состоянию, статусу и поиском по адресу и
  кадастровому номеру.
- **Адаптивный опрос** по шести признакам. Вопросы, лишённые смысла, не задаются; источник
  сведений по каждому признаку подсказывается. Незавершённое заполнение сохраняется.
- **Движок правил** — 61 сценарий ТЗ. Объект с несколькими состояниями получает несколько
  исходов, упорядоченных по приоритету.
- **Обработка пробелов матрицы.** Если комбинации нет в ТЗ, показываются ближайшие сценарии с
  указанием расходящихся признаков; решение нельзя утвердить до рассмотрения методологом.
- **Дорожная карта** — порядок действий как чек-лист поручений со сроками.
- **Протокол проверки** в .docx и .pdf: карточка объекта, все ответы опроса с источниками
  сведений, определённый сценарий и порядок действий. Хранится в системе постоянно, выгружается
  файлом, при утверждении решения формируется автоматически и больше не изменяется.
- **Фиксация авторства** — автор, время и отпечаток решения. Утверждённая проверка неизменяема.
- **Админка** — учётные записи, муниципалитеты, конструктор правил с отчётом о покрытии,
  очередь обращений к методологу, журнал действий.

## Бот в MAX

Упрощённая версия для тех, кому не нужен портал целиком. Сотрудник открывает бота, нажимает
«Завести дело», вводит сведения об объекте, проходит тот же адаптивный опрос и получает справку:
сжатую выжимку в чат и полный документ файлом.

```bash
cd backend && BOT_MAX_TOKEN=<токен> python -m bot
```

Бот **импортирует движок портала**, а не копирует правила: матрица сценариев остаётся в одном
месте. Базы данных ему не требуется — состояние диалога живёт в памяти, ничего не сохраняется.
Это проверяется тестом, который импортирует модули бота подпроцессом с вычищенными переменными
базы. Подробности и грабли MAX — [`docs/max-bot.md`](docs/max-bot.md).

## Роли

| Роль | Права |
|---|---|
| Специалист ОМСУ | Дела своего МО: создание, опрос, решение, дорожная карта, утверждение |
| Наблюдатель | Только чтение дел своего МО |
| Методолог | Чтение всех МО, матрица правил, рассмотрение обращений |
| Оператор системы | Всё перечисленное плюс учётные записи, муниципалитеты и журнал |

Специалист не видит дел чужого МО: они возвращают 404, а не 403, чтобы не раскрывать факт
существования дела.

## Запуск

### Railway

Одной службой: FastAPI отдаёт и API, и собранный фронтенд. Подключите репозиторий, добавьте
плагин PostgreSQL и задайте `APP_SECRET_KEY` и `APP_BOOTSTRAP_OPERATOR_PASSWORD` — без них
приложение намеренно не поднимется. Подробно: [`docs/deploy-railway.md`](docs/deploy-railway.md).

### Docker, один образ

Тот же образ, что уходит на платформу:

```bash
docker build -t portal:railway .
docker run -p 8000:8000   -e DATABASE_URL="postgresql://user:pass@host:5432/portal"   -e APP_SECRET_KEY="$(python -c 'import secrets;print(secrets.token_urlsafe(48))')"   -e APP_BOOTSTRAP_OPERATOR_PASSWORD="смените-пароль"   portal:railway
```

### Docker Compose, раздельно

Вариант для собственного контура: nginx отдаёт фронтенд, бэкенд — отдельная служба.

```bash
cp .env.example .env
# заполните APP_SECRET_KEY и APP_BOOTSTRAP_OPERATOR_PASSWORD
docker compose up --build
```

Портал — <http://localhost:8080>. При первом старте на пустой базе создаётся учётная запись
оператора из `.env`; **смените пароль после первого входа**.

### Локальная разработка

```bash
# Бэкенд
cd backend
python -m venv .venv && ./.venv/Scripts/python -m pip install -r requirements.txt
APP_DATABASE_URL="sqlite:///./dev.db" APP_AUTO_CREATE_SCHEMA=true APP_SECRET_KEY=dev \
  ./.venv/Scripts/python -m uvicorn app.main:app --port 8000

# Фронтенд
cd frontend && npm install && npm run dev
```

Документация API — <http://localhost:8000/docs>.

PDF формируется только при наличии в системе шрифта с кириллицей. В образе ставится
`fonts-dejavu-core`, на рабочем месте разработчика берётся системный Arial или DejaVu. Если
шрифта нет, портал предлагает только .docx, а не выдаёт нечитаемый файл.

### Демонстрационные данные

При работающем сервере:

```bash
cd backend && ./.venv/Scripts/python tools/seed_demo.py
```

Заводит муниципалитет, двух специалистов, методолога и четыре дела. Пароль учётных
записей печатается в вывод. В рабочий контур не заливать.

## Тесты

```bash
cd backend && ./.venv/Scripts/python -m pytest
```

321 тест. Ключевая часть — каждый из 61 сценария ТЗ прогоняется отдельным тестом: если правка
движка изменит исход, тест назовёт конкретный номер сценария и связку. Отдельный файл
`tests/test_regressions.py` закрывает случаи, при которых решение могло быть утверждено без
основания.

## Матрица сценариев

Правила выгружены из исходного .docx машинно и лежат в `backend/app/seed/rules_seed.json`.
Пересборка после правки ТЗ:

```bash
cd backend
python tools/extract_tz.py "путь/к/ТЗ.docx"
```

Инструмент проверяет выгрузку и отказывается писать seed, если в документе есть противоречия:
сценарий без способа, способ с пустым порядком действий, дублирующиеся условия внутри связки,
признак «наследники» при живом правообладателе.

Правила из ТЗ нельзя переписать через интерфейс — только отключить. Методолог добавляет
собственные правила, они помечаются отдельно и переживают перезаливку матрицы.

## Что не входит в объём

| Не реализовано | Документ |
|---|---|
| Этапы 1–3 ТЗ (выявление, идентификация, запросы в органы) | [`docs/analysis.md`](docs/analysis.md) |
| Обмен данными с ЦИУН | [`docs/ciun-integration.md`](docs/ciun-integration.md) |
| Усиленная квалифицированная электронная подпись | [`docs/signature.md`](docs/signature.md) |

Развёртывание на Railway описано отдельно: [`docs/deploy-railway.md`](docs/deploy-railway.md).

## Структура

```
Dockerfile       единый образ для Railway: сборка фронтенда + бэкенд
railway.toml     параметры платформы: Dockerfile, проверка состояния
docker-compose.yml  раздельный вариант для собственного контура
backend/
  bot/             бот в MAX: диалог, клиент платформы, справка
  app/
    engine/        движок: признаки, применимость, сопоставление правил
    documents/     протокол проверки: структура, writers для .docx и .pdf
    api/           маршруты FastAPI
    seed/          матрица, выгруженная из ТЗ
    models.py      схема данных
    services.py    прикладная логика
  tools/
    extract_tz.py  пересборка матрицы из исходного .docx
  tests/           321 тест
frontend/
  src/pages/       экраны портала
  src/api.ts       клиент API
docs/              аналитика, развёртывание, бот, контракт интеграции, подпись
```
