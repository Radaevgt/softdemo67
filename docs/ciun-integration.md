# Интеграция с ЦИУН: контракт на будущее

**Статус: не реализована.** Этот документ фиксирует, как система подготовлена к подключению,
чтобы интеграция не потребовала переписывать схему данных.

Действующая система: <https://map.scancontrol.ru/>

## Что просит заказчик

Из опросника:

- ответ № 4 — дополнительные сведения об объекте берутся из ЦИУН;
- ответ № 5 — накопителем является ЦИУН, формы документов подгружаются оттуда;
- ответ № 6 — отчёт и итоговые документы хранятся в ЦИУН постоянно.

То есть ЦИУН выступает и источником сведений об объекте, и хранилищем результата.

## Что уже заложено

В таблице `object_case`:

| Поле | Назначение |
|---|---|
| `ciun_object_id` | Идентификатор объекта в ЦИУН, индексирован |
| `ciun_synced_at` | Время последней синхронизации |

Оба поля не заполняются и не используются в логике. Они существуют, чтобы добавление
интеграции не требовало миграции с перестройкой таблицы дел.

## Предлагаемый контракт

### Направление «ЦИУН → портал»: сведения об объекте

Портал запрашивает карточку по кадастровому номеру и предзаполняет дело.

```
GET /integration/objects?cadastral_number=52:20:0100021:56
```

```json
{
  "ciun_object_id": "OKS-4412",
  "cadastral_number_oks": "52:20:0100021:56",
  "cadastral_number_land": "52:20:0100021:9",
  "address": "Нижегородская обл., г. Бор, ул. Полевая, д. 2",
  "object_kind": "izhs",
  "area": 68.4,
  "floors": 1,
  "wall_material": "деревянные",
  "municipality_code": "22740000"
}
```

Поля `object_kind`, адрес и кадастровые номера ложатся в карточку напрямую. Остальные —
справочные: на этапе 4 они на решение не влияют, но нужны сотруднику для сверки.

### Направление «портал → ЦИУН»: утверждённое решение

После утверждения проверки портал передаёт результат в ЦИУН как накопитель.

```
POST /integration/decisions
```

```json
{
  "ciun_object_id": "OKS-4412",
  "assessment_id": "0f2c…",
  "decided_at": "2026-09-17T09:14:22Z",
  "approved_by": {"login": "ivanova", "full_name": "Иванова Мария Петровна"},
  "content_hash": "09e77ebb…",
  "ruleset_version": "6dd8fc9c",
  "outcomes": [
    {
      "state": "fpo",
      "scenario_num": 3,
      "methods": [
        {"code": "FPO_DEMOLITION.v1", "title": "Демонтаж остаточных элементов ФПО"}
      ]
    }
  ],
  "roadmap": [
    {"order": 0, "text": "Создание межведомственной комиссии…", "status": "done"}
  ]
}
```

Тело ответа `POST /api/assessments/{id}/approve` уже содержит все эти данные — отдельная сборка
не потребуется.

### Формы документов

Ответ № 5 требует подгружать формы документов. Предлагается справочник соответствия
«способ → перечень форм», который ведёт ЦИУН:

```
GET /integration/document-templates?method_code=FPO_DEMOLITION.v1
```

Портал показывает ссылки на формы рядом с шагами дорожной карты. Хранение самих форм остаётся
в ЦИУН, дублировать их в портале не нужно.

## Открытые вопросы к владельцу ЦИУН

Ответы на них определят объём работ; без них оценка невозможна.

1. **Протокол и аутентификация.** REST с сервисным токеном, mTLS, интеграционная шина?
2. **Направление инициативы.** Портал опрашивает ЦИУН по запросу пользователя или ЦИУН
   push-ом отдаёт изменения?
3. **Владелец записи.** Если сведения об объекте правятся и там, и там — чья версия
   побеждает при расхождении?
4. **Идентификатор.** Кадастровый номер как ключ ненадёжен: у ранее учтённых объектов его может
   не быть (этап 2 ТЗ прямо про это). Нужен внутренний идентификатор ЦИУН.
5. **Доступность.** Что делает портал, если ЦИУН недоступен в момент утверждения решения —
   блокировать утверждение или ставить передачу в очередь? Рекомендация: очередь с повтором,
   иначе недоступность внешней системы остановит работу ОМСУ.
6. **Разграничение доступа.** Совпадают ли учётные записи и границы МО в двух системах, или
   нужна сверка справочников?

## Порядок подключения, когда ответы будут

1. Слой-адаптер `app/integrations/ciun.py` с интерфейсом и заглушкой — логика портала
   обращается только к интерфейсу.
2. Заполнение `ciun_object_id` при создании дела.
3. Фоновая очередь передачи утверждённых решений с повтором при недоступности.
4. Тесты на адаптере с подменой внешней системы.

Ни один из шагов не затрагивает движок правил и схему проверок.
